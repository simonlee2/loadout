# The Loadout macOS app bundle

Loadout ships two ways from one codebase:

- **SwiftPM** — `swift run Loadout` for fast local dev. All real code lives in the
  `LoadoutKit` library target (`Sources/Loadout/`); a thin `Loadout` executable
  target (`Sources/LoadoutMain/main.swift`) just calls `LoadoutApp.main()`.
- **A signable `.app`** — an Xcode project generated by
  [xcodegen](https://github.com/yonaskolb/XcodeGen) from `App/project.yml`. Its
  `Loadout` app target contains only `App/LoadoutAppShell/main.swift`
  (`import LoadoutKit; LoadoutApp.main()`) and depends on the local SwiftPM
  package's `LoadoutKit` product. This is the bundle that will later carry
  CloudKit entitlements and a Developer ID / distribution signature.

Both entry points are one line, so the app and the CLI can never drift.

## Regenerate the Xcode project

The `.xcodeproj` is generated and git-ignored — never edit it by hand. After
changing `App/project.yml` (or adding files under `App/LoadoutAppShell/`):

```sh
brew install xcodegen          # once
cd App
xcodegen generate --spec project.yml
```

## Build the app

```sh
cd App
set -o pipefail
xcodebuild \
  -project LoadoutApp.xcodeproj \
  -scheme Loadout \
  -configuration Debug \
  -derivedDataPath build/dd \
  build
```

The bundle lands at `build/dd/Build/Products/Debug/Loadout.app`. Launch it with
`open -n <path>/Loadout.app`.

> **Scheme note:** `App/project.yml` defines an explicit *shared* scheme named
> `Loadout`. This is deliberate. The SwiftPM package also vends an executable
> product called `Loadout`, and Xcode would otherwise auto-generate a second
> scheme with the same name; `-scheme Loadout` would then resolve
> nondeterministically and sometimes build the bare CLI binary instead of the
> `.app`. The shared scheme claims the name and keeps builds repeatable.

## Where entitlements live

Two plists in `App/`:

- **`Loadout.entitlements`** — an empty `<dict/>`. Used now so the app builds and
  ad-hoc signs without an Apple Developer account. Referenced by
  `CODE_SIGN_ENTITLEMENTS` in `project.yml`.
- **`Loadout+CloudKit.entitlements`** — the real entitlements for later:
  `com.apple.developer.icloud-services = [CloudKit]` and
  `com.apple.developer.icloud-container-identifiers = [iCloud.com.cardinalblue.Loadout]`.
  Not wired up yet.

Current signing settings (in `project.yml`) are `CODE_SIGN_STYLE = Automatic`
and `CODE_SIGN_IDENTITY = "-"` (ad-hoc), so CI and dev machines can build with no
account or provisioning profile.

## What flips when real signing lands

In `App/project.yml`, under the `Loadout` target's `settings.base`:

1. **Keep** `CODE_SIGN_STYLE: Automatic`.
2. **Add** `DEVELOPMENT_TEAM: <TEAMID>` (the Cardinal Blue team id).
3. **Remove** `CODE_SIGN_IDENTITY: "-"` so Xcode picks a real
   Apple Development / Developer ID identity.
4. **Swap** `CODE_SIGN_ENTITLEMENTS: Loadout.entitlements` for
   `CODE_SIGN_ENTITLEMENTS: Loadout+CloudKit.entitlements`.

Then re-run `xcodegen generate` and rebuild. The iCloud container
`iCloud.com.cardinalblue.Loadout` must exist in the developer account and be
enabled for the App ID `com.cardinalblue.Loadout`.
